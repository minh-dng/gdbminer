# Literature Review

Fuzzing, the automated generation of malformed or unexpected inputs to trigger software faults, has become one of the most widely deployed techniques for vulnerability discovery in software systems. On conventional desktop and server platforms, coverage-guided mutation fuzzers such as AFL [[@zalewski2017american]] have found thousands of real-world vulnerabilities. However, the growing attack surface of embedded and Internet-of-Things (IoT) firmware presents a qualitatively different challenge: devices operate without standard operating system abstractions, rely on vendor-specific peripherals, and seldom produce observable crash signals when memory corruption occurs [[@muenchWhatYouCorrupt2018]]. Three recent surveys, Muench et al.’s seminal analysis of crash-detection limitations [[@muenchWhatYouCorrupt2018]], Eisele et al.’s systematic review of 42 embedded fuzzing approaches [[@eiseleEmbeddedFuzzingReview2022]], and Yun et al.’s ACM Computing Surveys treatment of the field [[@yunFuzzingEmbeddedSystems2023]], together confirm that applying fuzzing to this class of software requires solutions that address re-hosting, fault detection, and input structure simultaneously. The survey by Asmita et al. [[@asmitaBareMetalFirmwareFuzzing2025]] provides the most up-to-date taxonomy of bare-metal fuzzing, mapping existing systems along axes of emulation fidelity, instrumentation granularity, and supported architectures. A significant but underappreciated bottleneck is input validity. Embedded parsers implement tight, hand-coded recursive-descent grammars for communication protocols. Mutation-based fuzzers corrupt existing valid inputs byte-by-byte and rarely produce inputs that pass the first validation stage of such parsers, wasting the bulk of the execution budget on trivially rejected inputs [[@asmitaBareMetalFirmwareFuzzing2025]]. Grammar-based fuzzing directly addresses this by generating syntactically valid inputs from a formal context-free grammar [[@aschermannNAUTILUSFishingDeep2019]]; however, such grammars are almost never publicly available for firmware, and creating them manually is labour-intensive and error-prone. This creates a demand for automated grammar inference: the ability to derive an accurate grammar from a compiled binary with minimal human effort. Four grammar inference paradigms have emerged: white-box approaches that require source-level instrumentation to dynamically trace input handling during execution [[@gopinathMiningInputGrammars2020]], grey-box approaches that instrument the target program using a debugger without requiring source code [[@eiseleGDBMinerMiningPrecise2025]], black-box approaches that treat the parser as a membership oracle [[@arefinBlackboxContextfreeGrammar2025]], and purely static approaches that symbolically execute the parser's source code without any runtime execution [[@bettscheiderInferringInputGrammars2025]]. The following sections survey the literature that contextualises and motivates a comparison between these paradigms in the embedded domain.

## 1.1 Embedded Fuzzing: Device Classification and Fault Detection

Muench et al. [[@muenchWhatYouCorrupt2018]] provide the canonical taxonomy of embedded devices in their widely cited work, dividing devices into three types: Type-I devices run a recognisable OS and can be fuzzed with relatively conventional techniques; Type-II devices run an RTOS and require partial emulation; Type-III (bare-metal) devices implement all logic in a monolithic binary with no OS abstraction whatsoever. Most MCU-class IoT devices fall into the Type-II or Type-III categories, placing them in the most technically challenging regime for fuzzing.

A more fundamental problem identified by Muench et al. is that memory corruption on these devices frequently produces no observable crash. Unlike desktop programs protected by address-space layout randomisation and OS signal delivery, bare-metal firmware simply continues executing after a buffer overflow, corrupting unrelated state and failing only later, if at all. Their study demonstrates this by injecting controlled vulnerabilities into common open-source libraries (expat, mbed TLS), running them on real hardware, and finding that a significant fraction of injected faults produces no crash signal during a standard fuzzing run. The authors respond by implementing a set of runtime detection heuristics, tracking segment boundaries, heap metadata, stack canaries, and format-string specifiers, as plugins for the PANDA dynamic analysis platform, showing that all injected bugs are detectable with sufficient instrumentation [[@muenchWhatYouCorrupt2018]]. This “analysis plugin” architecture is an important design pattern for any integrated embedded fuzzing infrastructure: fault detection must be decoupled from the fuzzer and implemented as a composable, separately maintained layer. PANDA itself warrants note as a QEMU-derived platform that offers execution record-and-replay capabilities and LLVM-based dynamic taint analysis across multiple architectures [[@asmitaBareMetalFirmwareFuzzing2025]], making it a natural host for such detection heuristics. The 2025 survey by Asmita et al. [[@asmitaBareMetalFirmwareFuzzing2025]] provides the most comprehensive recent taxonomy of bare-metal fuzzing approaches, categorising them along axes of emulation fidelity (full emulation, partial emulation, hardware-in-the-loop), instrumentation granularity, and supported architectures (Cortex-M, RISC-V, MIPS). The survey identifies key open challenges including accurate peripheral modelling, scalable state-reset mechanisms, and standardised evaluation, and maps existing systems such as P²IM [[@fengP2IMScalableHardwareindependent2020]], μAFL, and Hoedur [[@scharnowskiHOEDUREmbeddedFirmware2023]] as potential integration points. Eisele et al.’s earlier 2022 review [[@eiseleEmbeddedFuzzingReview2022]] covers 42 tools and provides a formal definitional framework for embedded fuzzing, while Yun et al. [[@yunFuzzingEmbeddedSystems2023]] contribute a higher-level classification that distinguishes user-mode, full-system, and peripheral-proxying approaches. For the present research, these surveys collectively provide a map of the re-hosting landscape that any grammar-guided approach must operate within.

## 1.2 Re-Hosting Approaches

Because running firmware at scale on physical hardware is impractical, re-hosting, the emulation of firmware in software, is a prerequisite for high-throughput fuzzing. Emulators such as QEMU (supporting both CPU and device emulation), Unicorn (CPU-only, derived from QEMU), and Renode (which additionally simulates peripherals, sensors, and communication buses) form the infrastructure layer upon which re-hosting frameworks are built [[@asmitaBareMetalFirmwareFuzzing2025]]. The Avatar framework [[@zaddachAvatarFrameworkSupport2014]] and its successor Avatar² [[@muenchAvatar2MultiTargetOrchestration2018]] address the challenge of peripheral fidelity by orchestrating a hybrid approach: the firmware runs in a software emulator, but peripheral accesses are forwarded to real hardware over a debug interface. This preserves correctness for peripheral-heavy code paths while enabling software-level instrumentation and reset. Olivier et al.’s 2024 retrospective on Avatar² [[@oliverAvatar2artifacts2024]] documents the framework’s evolution since its 2017 release, cataloguing its use in over a dozen published studies on re-hosting and firmware fuzzing, and confirming its status as the most widely adopted orchestration framework in the domain. Avatar² is central to the pipeline proposed in this research.

Biondo et al. demonstrate Avatar2’s practicality in AFLtar [[@biondoCoverageguidedFuzzingEmbedded2019]], which combines Avatar2, the Unicorn engine, and AFL to create a coverage-guided fuzzer for STM32 firmware. The results are instructive: while coverage-guided fuzzing is feasible, execution rates of only a few dozen iterations per second on Expat-based targets highlight the throughput penalty of re-hosting. Critically, AFLtar uses mutation-based input generation, making no attempt to exploit parser structure, precisely the limitation that grammar-based approaches could address. More recent work has sought to improve re-hosting fidelity and throughput. P²IM [[@fengP2IMScalableHardwareindependent2020]] uses differential execution analysis to infer peripheral register access patterns and generate abstract peripheral models, reducing the need for manual modelling. Fuzzware [[@scharnowskiFuzzwareUsingPrecise2022]] uses symbolic execution to identify which peripheral inputs are actually relevant to firmware control flow and focus modelling effort accordingly, achieving substantially better throughput. Hoedur [[@scharnowskiHOEDUREmbeddedFirmware2023]] demonstrates that multi-stream, structured input representations improve fuzzing effectiveness on re-hosted MCU firmware, offering a bridge between structured input generation and the re-hosting infrastructure. These advances each improve a different layer of the re-hosting stack, but none connects it to grammar inference: grammar-guided input generation would be orthogonal to and composable with any of them. If re-hosting latency proves to be the primary bottleneck for grammar-guided fuzzing, two recent systems suggest mitigation paths. SAFIREFUZZ [[@seidelFormingFasterFirmware2023]] demonstrates near-native rehosting by running Cortex-M firmware as a Linux userspace process rather than emulating it instruction-by-instruction, reporting a 690× throughput increase over HALucinator during 24-hour campaigns. SHiFT [[@meraSHiFT2024]] takes a complementary semi-hosted approach, executing firmware partly on real hardware and partly in emulation. Both demonstrate that the emulation-fidelity/throughput trade-off is a design space, not a fixed constraint, and could serve as alternative re-hosting backends if Avatar² throughput proves insufficient for the proposed integration.

## 1.3 Grammar Inference: From Dynamic to Static Approaches

### 1.3.1 The Need for Grammars in Fuzzing

Grammar-based fuzzing, advanced by NAUTILUS [[@aschermannNAUTILUSFishingDeep2019]], generates inputs by sampling derivation trees from a user-supplied context-free grammar and applying mutation operators at the tree level rather than the byte level. This structural awareness dramatically increases the proportion of generated inputs that pass initial parsing, giving the fuzzer access to deeper code paths that mutation-based approaches rarely exercise. NAUTILUS demonstrates that coverage-guided grammar-based fuzzing outperforms AFL by an order of magnitude and purely generational grammar fuzzers by more than a factor of two when measuring code coverage [[@aschermannNAUTILUSFishingDeep2019]]. The fundamental limitation is the grammar specification bottleneck: grammars must be written by hand, which is feasible for well-documented protocols but impractical for proprietary or undocumented firmware parsers. Grammar mining, the automatic extraction of a formal input specification from a program, has therefore become a critical enabling technology for grammar-based fuzzing.

### 1.3.2 Grammar Mining Background

Grammar mining is the process of automatically extracting the formal specification of a program’s input language. This field has evolved from static analysis of source code to dynamic observation of program behaviour. Early tools like Autogram relied on data-flow analysis, tracking how substrings of the input were assigned to variables. The limitation was clear: if a program processed an input but did not explicitly store it in a named variable, the tool could not infer the associated grammar rule. The most direct predecessor of debugger-based grammar inference is Mimid [[@gopinathMiningInputGrammars2020]], which instruments Python programs during test execution, tracks which input positions are compared at each control-flow branch, and reconstructs a grammar from the resulting input-coverage map. Mimid operates on the principle that the dynamic program dependence tree, the sequence of function calls and branches taken during input processing, is structurally equivalent to a parse tree. By observing which code locations access which input bytes, Mimid can reconstruct a context-free grammar. This approach is highly effective for recursive-descent parsers, which make up roughly 80% of top programming language parsers [[@gopinathMiningInputGrammars2020]]. Its successor Cmimid extended this to C programs. However, both require source-level instrumentation and are not applicable to compiled binaries, a critical limitation in the embedded context where source code is rarely available and binaries are produced by toolchains that apply heavy optimisation.

### 1.3.3 Grey-Box Inference: GDBMiner

GDBMiner [[@eiseleGDBMinerMiningPrecise2025]] represents the most important advance for the present research questions, extending the Mimid paradigm to compiled binaries using only a GDB-compatible debug interface. Because GDBMiner relies on observing internal program state (via hardware watchpoints and single-stepping) without requiring source code, it is best classified as a grey-box approach: it has more visibility than a black-box oracle-based method, but does not require the full source access that white-box or static analyses demand. The tool single-steps the target binary, uses hardware watchpoints to track which code locations access which input bytes, reconstructs a control-flow graph and a corresponding derivation tree for each input, and then applies an active-learning merge process to produce a compact context-free grammar. The design is deliberately constrained to what is available on resource-limited embedded targets: no source code, no compiler instrumentation, and as few hardware watchpoints as the hardware provides (the STM32L4 provides only four). The paper’s embedded case study is its most significant contribution for the present research. On an STM32L4 board parsing JSON, GDBMiner successfully infers a high-precision grammar under the four-watchpoint constraint, though tracing time per input increases substantially compared to desktop execution. The authors report F1 scores competitive with black-box competitors on standard benchmarks, and superior precision on the embedded target. The paper’s evaluation focuses on grammar quality metrics, specifically precision, recall, and F1 score of grammar rules, and does not extend to measuring the effect of these inferred grammars on end-to-end fuzzing effectiveness. This is a natural scope limitation rather than a flaw, but it means the question of whether a high-quality inferred grammar translates into improved bug-finding remains open.

GDBMiner’s reliability also degrades when the target uses a separate lexer/parser architecture, which is common in production embedded code, and when aggressive compiler optimisations obscure the data-flow structure that the tool depends on. These are practical limitations that any follow-on study must account for. Overall, GDBMiner establishes that high-quality grammar inference from embedded binaries is feasible, but leaves open whether that inference is useful for downstream fuzzing.

### 1.3.4 Black-Box Inference: Arvada, TreeVada, and NatGI

Black-box grammar inference treats the parser as a membership oracle: given an input string, the oracle answers “accepted” or “rejected,” and the inference algorithm generalises from these responses to a grammar. This approach requires no debugger, no access to the binary, and no hardware interaction, making it highly portable. The trade-off is accuracy: without observing internal parser state, black-box methods must rely on statistical generalisation from a large number of oracle queries, and tend to produce grammars that are overspecific or overgeneral. NatGI [[@arefinBlackboxContextfreeGrammar2025]], the most recent and capable black-box approach, builds on its predecessors Arvada and TreeVada. It introduces a “bubble exploration” strategy that proposes candidate non-terminals by identifying syntactically interchangeable substrings, then applies hierarchical delta-debugging to simplify derived parse trees. On benchmarks spanning toy languages through Lua, C, and MySQL, NatGI achieves an average F1 score of 0.57, which is 25 percentage points higher than the best-performing baseline (TreeVada), and produces more compact, interpretable grammars [[@arefinBlackboxContextfreeGrammar2025]]. The critical limitation of NatGI for the embedded domain is the oracle assumption. Black-box inference requires the ability to submit arbitrary candidate strings to the parser and observe acceptance or rejection. On a re-hosted embedded target via Avatar², this requires resetting firmware state between each query, an expensive operation that may cost several seconds per call. At the scale of oracle queries required by NatGI for larger grammars, the wall-clock time for inference could become prohibitive. This cost has not been empirically characterised in the embedded context. A direct comparison of GDBMiner and NatGI under embedded re-hosting conditions, measuring both inference cost and grammar quality, is absent from the literature.

### 1.3.5 Static Inference: STALAGMITE

A third grammar inference paradigm has recently emerged that sidesteps the dynamic analysis overhead entirely. STALAGMITE [[@bettscheiderInferringInputGrammars2025]], introduced by Bettscheider and Zeller in 2025, performs purely static symbolic analysis of recursive-descent parsers. The tool associates each parser function parse_ELEM() with a non-terminal <ELEM>, limits recursive calls and loop iterations to ensure a finite number of symbolic paths, and for each path creates an expansion alternative for the corresponding non-terminal. Being entirely static, STALAGMITE requires no seed inputs, no execution, and no debugger. Applied to parsers for complex languages such as TINY-C and JSON, the implementation extracts grammars with an accuracy of 99-100%, substantially outperforming dynamic approaches [[@bettscheiderInferringInputGrammars2025]]. STALAGMITE’s significance for the present research is twofold. First, it establishes a theoretical upper bound on grammar inference accuracy that dynamic approaches (both grey-box and black-box) have not yet matched. Second, its limitations clarify why dynamic approaches remain necessary for the embedded domain. STALAGMITE requires access to the parser’s source code and, importantly, depends on a specific parser structure: it assumes that each syntactic category is implemented by a clearly named function (e.g. parse_json_object), which it then maps to a non-terminal. Adapting it to a new parser therefore requires non-trivial effort in understanding and potentially annotating the parser’s source, and this structure is simply unavailable for closed-source firmware binaries. Nevertheless, STALAGMITE presents a distinct paradigm of grammar inference that may complement dynamic approaches in future work where parser source code is available.

### 1.3.6 White-Box Inference

White-box grammar inference requires source-level instrumentation to track data flow during parsing of sample inputs. Mimid [[@gopinathMiningInputGrammars2020]] and its C-language successor Cmimid label input characters with their execution context (the active call stack at the point of comparison) and use this mapping to derive parse trees, which are then generalised into a context-free grammar. This approach is highly effective for recursive-descent parsers and forms the conceptual foundation for GDBMiner’s grey-box extension to compiled binaries. However, the requirement for source code and compiler-level instrumentation means that white-box inference is not applicable to the closed-source firmware targets that motivate this research. It remains relevant as a reference point: on targets where source is available, white-box tools can produce high-quality grammars that serve as baselines for evaluating grey-box and black-box alternatives.

## 1.4 Grammar-Based Fuzzing Engines

Two paradigms of input generation dominate grammar-based fuzzing: generation-based approaches that sample fresh derivation trees from the grammar, and mutation-based approaches that modify existing trees. NAUTILUS [[@aschermannNAUTILUSFishingDeep2019]] unifies both, implementing coverage-guided input generation that samples and mutates parse trees and integrates with AFL’s edge-coverage feedback mechanism. Its most impactful mutation operator is the splicing method, which recombines subtrees from different derivations to produce novel but structurally valid inputs. NAUTILUS demonstrates substantially higher bug-finding rates than mutation-based AFL on interpreters for mruby, ChakraCore, and PHP [[@aschermannNAUTILUSFishingDeep2019]]. However, NAUTILUS has not been evaluated on embedded firmware targets, and assumes that the fuzzing engine and the target run in the same execution environment, an assumption that breaks down in Avatar²-based re-hosting where inputs must be serialised over a debug or network interface. Adapting NAUTILUS to drive fuzzing through an Avatar² orchestration layer would require a custom input delivery mechanism, and the throughput impact of this interface has not been studied. Grammarinator [[@hodovanGrammarinatorGrammarbasedOpen2018]] offers a complementary approach, generating inputs from ANTLR v4 grammar specifications and use the same grammar to analyse and evolve existing test sets. A key practical advantage is grammar representation and reuse: Grammarinator directly consumes ANTLR v4 grammars (lexer and parser combined), so it can immediately reuse hundreds of existing grammars from the public ANTLR repository, greatly reducing modelling effort for common languages and formats. Grammarinator has been used successfully to find over 100 bugs in JavaScript engines [[@hodovanGrammarinatorGrammarbasedOpen2018]]. While less sample-efficient than NAUTILUS, it is simpler to integrate and has been applied to a wider range of languages. Neither tool has been evaluated on embedded firmware. Zamudio Amaya [[@zamudioamayaShapingTestInputs2024]] addresses a subtler question: within grammar-based fuzzing, how should the sampling distribution over grammar rules be shaped to maximise effectiveness? This work demonstrates that biasing which grammar rules are sampled, rather than treating all alternatives as equally likely, can substantially improve coverage and bug-finding rates. The insight is directly relevant as an extension to NAUTILUS’s sampling strategy and suggests that even after a grammar has been inferred, there remains scope for optimising how it is used during fuzzing. A longer-term gap is the absence of constraint-augmented grammar fuzzing for embedded targets. For many embedded protocols, structural validity alone is insufficient: semantic constraints (such as a length field matching the payload length) are necessary to pass deeper parser stages. GDBMiner’s output is limited to context-free grammars without semantic annotations, and no work has explored how such constraints could be derived automatically from embedded binaries.

## 1.5 Benchmarking and Evaluation Infrastructure

FuzzBench [[@metzmanFuzzBenchOpenFuzzer2021]] provides the standardised, cloud-based benchmarking platform that has become the de facto methodology template for desktop fuzzer comparison. FirmReBugger [[@duongFirmReBuggerBenchmarkFramework2026]] is the first systematic attempt to adapt this rigour to embedded firmware fuzzing. It introduces FirmBench, a corpus of 61 binary targets compiled from open-source embedded libraries, each annotated with 313 bug oracles expressed as C-style expressions over CPU register and memory state. Crucially, the framework distinguishes three stages of fault manifestation: reached (execution arrives at the vulnerable location), triggered (the vulnerability is actually exercised), and detected (the oracle fires). This taxonomy directly addresses the finding by Muench et al. [[@muenchWhatYouCorrupt2018]] that embedded bugs are often triggered without being detected. The framework is fuzzer-agnostic and requires no modification to target binaries. However, FirmReBugger evaluates nine existing fuzzers, none of which are grammar-guided, and has not been used to compare grammar-based and mutation-based input generation strategies. This is a significant gap: the framework’s bug-oracle methodology and its separation of the benchmark from the fuzzer under test make it ideally suited to evaluate whether grammar-guided input generation improves bug detection rates over mutation-based baselines. FirmReBugger’s design, replaying fuzzing seeds against oracles without modifying the target binary, means that a grammar-based fuzzer can be integrated and evaluated with minimal framework adaptation, provided the fuzzer produces seed files in a compatible format. The present research adopts FirmReBugger’s reached/triggered/detected taxonomy and a subset of its FirmBench targets as the evaluation infrastructure for the proposed grammar-guided fuzzing comparison.

## 1.6 Summary of Gaps

The surveyed literature reveals a well-populated but fragmented landscape. Capable re-hosting frameworks, promising grammar inference tools, powerful grammar-based fuzzers, and nascent benchmarking infrastructure each exist independently, but the connections between them have not been made. Three specific gaps are directly relevant to the present project. First, there is no end-to-end evaluation of grammar-guided fuzzing on embedded firmware. GDBMiner [[@eiseleGDBMinerMiningPrecise2025]] evaluates grammar quality but not fuzzing outcomes. NAUTILUS [[@aschermannNAUTILUSFishingDeep2019]] evaluates grammar-based fuzzing but on desktop interpreters. AFLtar [[@biondoCoverageguidedFuzzingEmbedded2019]] demonstrates coverage-guided fuzzing on firmware but uses mutation-based input generation. No study has closed the loop: infer a grammar from an embedded binary, feed that grammar to a grammar-guided fuzzer, and measure bug detection outcomes against a mutation-based baseline. Second, the integration interfaces between existing tools have not been standardised or prototyped. GDBMiner outputs a context-free grammar in an internal format; NAUTILUS expects grammars in a specific text notation; Avatar² exposes a Python API for orchestrating firmware execution. Connecting these three systems requires adapter code that has not been publicly described or evaluated. The engineering barriers, including format incompatibilities, execution model mismatches, and latency penalties, are currently unknown.
## 2 Research Proposal

The literature review identifies a clear and bounded gap: no prior work has connected a grammar inferred from an embedded firmware binary to a grammar-guided fuzzer and evaluated the resulting system against mutation-based baselines. Furthermore, the engineering cost of building this integration through an Avatar² re-hosting layer is unknown. This research addresses both gaps through two research questions and corresponding contributions.

### 2.1 Research Questions and Contributions

RQ1: What adapter design is required to connect GDBMiner’s grammar output to NAUTILUS via an Avatar²-based firmware re-hosting environment, and what is the primary engineering barrier, whether format incompatibility, execution model mismatch, or throughput degradation, that limits the practical applicability of this integration pipeline on the selected firmware targets? This question is primarily a design and implementation study. It requires building a working prototype of the integration pipeline, documenting the adapter interfaces required at each boundary (GDBMiner output to NAUTILUS grammar format; NAUTILUS input delivery to Avatar² execution interface), and characterising the throughput and latency profile of the resulting system. A working prototype that achieves even a modest fuzzing rate on one or two re-hosted targets would represent a novel contribution, since no such integration currently exists in the literature. The question is deliberately scoped to barrier identification rather than full optimisation, which would be unrealistic within four months. A failure mode to guard against is that Avatar²-based re-hosting latency makes grammar-guided fuzzing impractical regardless of grammar quality, in which case the contribution would be a documented negative result, itself valuable for guiding future work toward alternative re-hosting backends such as SAFIREFUZZ [[@seidelFormingFasterFirmware2023]] or SHiFT [[@meraSHiFT2024]]. RQ2: How does the grammar-guided fuzzing pipeline (the “fork”) compared to existing embedded fuzzers when evaluated through the lens of FirmReBugger? This question uses FirmReBugger’s [[@duongFirmReBuggerBenchmarkFramework2026]] benchmarking infrastructure and reached/triggered/detected taxonomy to position the integrated pipeline against mutation-based baselines. The comparison is not expected to demonstrate superiority across all targets, since the grammar-guided approach is a prototype, but rather to characterise which target, and bug classes benefit from grammar-guided input generation and which do not. The intended contributions are as follows.

1. A working prototype adapter that connects GDBMiner’s grammar output to the NAUTILUS grammar-based fuzzer via an Avatar²-based firmware re-hosting environment (RQ1). This constitutes the first published integration of these three tools, and a reusable pipeline that future researchers can extend with additional inference tools or fuzzing engines.

2. A characterisation of the primary engineering barriers to this integration, covering format incompatibility, execution model mismatch, and throughput degradation, serving as a practical guide for future research (RQ1).

3. A comparative evaluation of the integrated pipeline against fuzzers in the FirmReBugger suite using FirmReBugger’s bug-oracle methodology, reporting coverage growth and bug-state outcomes across a fixed set of firmware targets (RQ2).

### 2.2 Methods

The research is structured in three sequential stages, with stages two and three overlapping to permit adapter design decisions to be informed by Stage 1 observations. Throughout development, the source code of FirmWire [[@hernandezFIRMWIRETransparentDynamic2022]] and the WYCINWYC analysis plugins [[@muenchWhatYouCorrupt2018]] serve as practical references for how Avatar² orchestration and PANDA-based fault detection have been implemented in prior work; the integration patterns in both codebases directly inform the adapter design. In Stage 1 (weeks 1-6), three to five parser targets are selected from open-source embedded libraries also present in FirmBench [[@duongFirmReBuggerBenchmarkFramework2026]], specifically libraries implementing well-documented text-based protocols with documented golden grammar so that generated grammar quality can be assessed against a known ground truth. GDBMiner is run on each target in an Avatar² re-hosted environment on a representative STM32-class MCU emulated via PANDA. Inference wall-clock time and grammar F1 score against the ground-truth grammar are recorded for each target. In Stage 2 (weeks 4-10), implement an adapter such that (a) translates GDBMiner’s internal grammar representation into NAUTILUS’s input format, and (b) implements a NAUTILUS input delivery driver that serialises generated inputs over Avatar²’s virtual UART interface to the re-hosted firmware. The adapter design is documented as a structured implementation diary recording each integration decision, the time spent on it, and the root cause of any incompatibility encountered. In Stage 3 (weeks 8-14), the grammar-guided NAUTILUS pipeline is integrated into the FirmReBugger benchmarking framework. Fuzzing campaigns of fixed duration (24 hours per target) are run on the selected FirmBench targets using the GDBMiner-inferred grammars. The firmware images are annotated with FirmReBugger’s bug oracles for the subset of bugs that intersect with the selected targets. Metrics are collected at one-hour intervals to produce coverage growth curves, and bug-state outcomes (reached/triggered/detected) are recorded at the end of each campaign. Three independent trials are run per target to account for the inherent non-determinism of fuzzing. The resulting data are then compared against the published results for the nine mutation-based fuzzers already evaluated in FirmReBugger’s benchmark suite, which provides a controlled, like-for-like comparison on the same targets and bug oracles. To ensure reproducibility, all experiments are conducted within a virtual machine with full command logging. The final two weeks are reserved for analysis and write-up.

### 2.3 Evaluation

For RQ1, the primary evaluation is throughput, measured in generated-and-executed inputs per second. Engineering barriers are documented through the structured implementation diary described above, categorised by root cause (format incompatibility, execution model mismatch, or throughput degradation). Grammar F1 score is measured by comparing GDBMiner’s inferred grammar rules against the ground-truth grammar derived from open-source parser source. Structural validity rate is measured by generating 10,000 inputs from the inferred grammar using NAUTILUS in generation-only mode and submitting them to the re-hosted firmware, recording the proportion accepted. These metrics together characterise both the quality of the integration (throughput, validity rate) and the barriers encountered during its construction. For RQ2, bug detection outcomes are compared against the published results of the nine fuzzers evaluated in FirmReBugger [[@duongFirmReBuggerBenchmarkFramework2026]], using the reached/triggered/detected taxonomy. For each bug in the annotated target set, the number of trials (out of three) in which the bug reaches “detected” status within the 24-hour budget is reported for the grammar-guided pipeline and compared to the corresponding rates reported for the existing fuzzers on the same targets. Code coverage growth curves are plotted at one-hour intervals to visualise whether grammar-guided input generation achieves deeper coverage earlier. Given the small number of trials afforded by the time budget, results are presented descriptively with a discussion of effect size and direction. Where the grammar-guided pipeline outperforms existing fuzzers on specific bug classes, the relationship between bug location and the grammar rule governing the relevant input region is discussed qualitatively to establish a plausible mechanism for improvement.
