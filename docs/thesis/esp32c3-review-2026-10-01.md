# ESP32-C3 implementation and paper alignment review

Reviewed the current worktree on `experiment/esp32-c3`, including the uncommitted adapter, firmware ports and
September 30 evidence. The reference is Eisele et al., *GDBMiner: Mining Precise Input Grammars on (Almost) Any
System*, [DOI 10.4230/LITES.10.1.1](https://doi.org/10.4230/LITES.10.1.1), especially Sections 4.1, 5.4 and 6.
Thesis scope comes from `obsidian-personal/Uni/Thesis/research questions.md`, `GDBMiner replication hub.md` and
`Replication/ESP32-C3 paper replica 2026-09-30.md`.

## Assessment

The current C3 implementation is a close port of the paper's tracing and grammar-mining workflow. It uses the
reference parser libraries and serial acceptance rules, observes actual hardware reads, repeats execution across
watchpoint windows, and runs the repository miner and evaluator. Earlier bitmap, custom-parser and ROM-unwinder
experiments are historical stages, not the current method.

It does not reproduce the mutation-fuzzer comparison in Section 5.4, and its timings are not a controlled
processor-speed comparison. No final mutation-baseline result was found in the reviewed C3 run directories;
the comparison runner does exist, with qualifications below. The platform, debug transport, host, compiler and
available watchpoint counts differ. No new
STM32 hardware baseline was established in this review. This primarily supports the thesis's portability question,
RQ2. It does not complete RQ1 or establish RQ3's fidelity between manual and automated execution.
Repeated reliability measurements and controlled timing comparisons are extensions needed for those stronger
claims, not additional requirements stated by the paper's embedded case study.
The paper names B-L475E-IOT01A, while all three current STM32 PlatformIO configurations select
`disco_l4s5i_iot01a`. Preserve that reference-identity mismatch in the thesis rather than treating the current
artifact configuration as proof of the historical board setup.

## Findings and changes

1. **High: CGI decode overflowed its output array at the advertised input limit. Fixed in source.**
   `example_firmware/esp32-c3_cgidecode/src/main.cpp`, `parser()`, allocated 2,048 bytes for decoded output.
   `percent::decode` writes all 2,048 bytes of an unescaped input and then writes a NUL. An AddressSanitizer build
   of the actual parser body with the installed `percent_encode` source reproduced a one-byte stack overflow.
   The array now has 2,049 bytes, and the same check passes. The library and acceptance rule are unchanged.
   Existing ELFs, traces and measurements predate this fix. A successful serial reply in the earlier capacity
   check did not establish memory safety.

2. **Medium: the current XML configuration omitted a setting used in its timing result. Fixed.**
   The retained `xml-full/configuration.ini` (now `output/esp32-c3_xml/trial-0/`) sets `breakpoint_always_inserted = true`; the current target INI did
   not. Restored that option. The existing adapter already implements it. The September 30 A/B record reports
   244 seconds with the option and 271 seconds without it for `input.9`, with identical traces. This change
   aligns the default configuration with the measured run; it is not a new performance measurement.

3. **Medium: XML's score does not establish that the inferred grammar understands nesting.**
   The wrapper intentionally matches the reference and never calls `yxml_eof`. It accepts some incomplete XML.
   `src/miner/mine.py::check_empty_rules` removes all nullable occurrences together, rather than generating
   every nullable-occurrence combination. With the current deletable markers and epsilon removal, the recorded
   token probe is `<b>R<` and text becomes alphanumeric. Removing the text-class marker gives `<b>R` and printable
   text; replacing epsilon removal with the textbook version also gives printable text in the retained ablation. Printable text can
   consume nested markup and malformed XML. The retained published grammar gets 100% recall on this corpus,
   while Table 8 reports 93.5%. Those are distinct measurements. Neither number proves recursive XML inference.
   Preserve the reference oracle and miner for replication; a strict EOF oracle or epsilon-removal correction
   belongs in a separately labelled experiment with fresh mining and evaluation.

4. **Medium: completion and timing claims need narrower wording.**
   The 20 XML traces combine an interrupted run and a resumed run. The reported 07:29:05 excludes the lost
   portion of `input.11` and recovery wait. It is retained successful tracing time, not uninterrupted elapsed
   time or a reliability estimate. The 4.5–6.8 timing ratios compare whole setups, including 6/8/7 watchpoints
   on C3 versus four in the paper. They do not isolate RISC-V, the CPU or the adapter as the cause.

5. **Medium: some operational and thesis documentation describes superseded states.**
   The Obsidian hub still has “planned” handoff text and a warning that an uninstrumented tracer remains to be
   implemented. Its linked September 30 note records the completed hardware-trigger implementation. The
   repository replica record's Section 4 previously presented v1 recording of skipped-function reads as the final
   behavior. This review corrected that passage: Section 7 and the current adapter discard those reads, as the
   published STM32 traces do. The Obsidian hub's stale planning text has not been edited.
   Resolved on 2026-10-01: each target INI writes to `output/esp32-c3_<target>/`, and the retained final run is
   that directory's `trial-0/`, which `find_output_directory` selects. A new trace creates `trial-1/`, which
   mining and evaluation then select instead.

6. **Remaining limitation: serial recovery is timing-dependent and retries are unbounded.**
   `ESP32SerialConnection.send_input` resends after a restart marker and a grace interval without a result.
   That cannot distinguish a lost packet from a parser held at a breakpoint longer than the interval.
   `SUTConnection.input_accepted` also retries every timeout without a maximum. These are code-level limits,
   not evidence that the corrected September 30 mining runs were misaligned. The retained per-query checks
   found no disagreements in those runs. For RQ3, record retries and bound experiment duration externally;
   test reset-during-query and delayed-result cases before claiming general reset tolerance.

The inherited `percent_encode` trailing-percent over-read and unsequenced increments remain documented reference
limitations. The capacity fix above does not repair them. Do not equate agreement on the valid corpus with
agreement on every malformed input or compiler.

## Recheck: what the remaining evidence gaps mean

These three gaps support different claims. They are not three implementation defects or three mandatory full
campaigns before the port can count as a result.

### Mutation-fuzzer comparison: a missing part of Table 8

Section 5.4 compares the acceptance rate of grammar-generated inputs with inputs mutated from the seed set.
Table 8 reports mutation acceptance of 79.5% for CGI decode, 20.8% for JSON and 10.1% for XML. This measures
whether generated inputs pass the parser. It does not measure bugs found, coverage or comparative fuzzing effectiveness.

`src/eval/compare_fuzzers.py` already runs a comparison. However, it imports the local `MutationFuzzer` from
`src/eval/grammar.py`, whereas the paper names the Fuzzing Book mutation fuzzer. The local implementation first
returns each seed unchanged, then applies 2–10 deletions, insertions or bit flips. Its seed order comes from an
unsorted directory iteration. No equivalence check against a pinned Fuzzing Book version was established here.
The runner also uses `CoverageFuzzer` for grammar generation, while `precision_recall.py` uses `LimitFuzzer`.
Its acceptance result therefore need not equal the existing precision result, even with the same grammar.

To complete this comparison, establish the baseline version and settings, preserve seed order and random state,
then send both candidate sets to the same firmware oracle. Save each candidate, decision and transport failure,
with the denominator. A proposed 1,000 attempts per arm is a practical matched budget; Section 5.4 does not give
enough detail to establish every historical mutation setting from its text alone. Do not call the local runner
an exact reproduction merely because its class is named `MutationFuzzer`. This comparison can reuse the retained
grammar and matching firmware; it does not itself require tracing or mining again.

### Reliability: evidence for the thesis questions

The paper's embedded case study does not report a repeated-run completion probability. The request to measure
completion and preserve failures comes from the thesis notes, especially `research questions.md` and
`Replication/Hardware automation harness.md`. RQ3 asks whether automation preserves the manual procedure's
artifacts, timings, outcomes and failures; repetition alone cannot establish that equivalence.

The retained XML evidence establishes eventual completion after recovery. It does not establish that a fresh
20-seed run will finish unattended. Report first-attempt completion separately from completion after retry,
successful tracing time separately from total elapsed time, and count resets, timeouts and manual interventions.
Define the unit as a seed attempt or a full campaign before calculating a completion proportion. Twenty seeds
in one recovered campaign are not twenty independent repetitions of that campaign.

A practical first extension is to repeat a fixed manual smoke procedure and its automated equivalent on the same
firmware, compare traces and oracle answers, and retain failures. Full campaigns are needed for claims about
long-run USB stability. Three to five repeats can provide a descriptive pilot, but are not a prescribed sample
size or strong evidence of a low failure probability. Existing diagnostic repeats remain useful evidence and
should be reported for the procedures they actually tested.

### Controlled timing: needed to explain a speed difference

It is valid to report C3 times alongside the paper's times with setup differences stated. A controlled experiment
is needed to attribute the difference to watchpoint capacity, polling, the debugger or processor architecture.
Four C3 watchpoints control one factor; they do not make C3 and STM32 otherwise equivalent.

For the current 20-seed corpora, the required window count is `sum(ceil(seed_bytes / watchpoints))`:

| Target | Four-watchpoint windows | Current C3 windows |
| --- | --- | --- |
| JSON | 50 | 34 with six watchpoints |
| CGI decode | 26 | 22 with eight watchpoints |
| XML | 97 | 62 with seven watchpoints |

These are calculated execution counts, not measured time ratios. Seed executions have different costs, and each
window also pays startup overhead. Compare four slots with the current allocation on the same C3, ELF, host,
GDB, OpenOCD, clock and seeds; keep enough free slots for breakpoints. Repeat paired measurements and check that
merged read observations agree. The existing polling, JTAG-clock and XML-breakpoint A/B experiments already
support their bounded configuration comparisons. They do not isolate the cause of the cross-platform ratio.

Priority depends on the claim: validate the corrected CGI firmware first; complete the mutation comparison for
a fuller Table 8 replication; collect manual-versus-automated evidence for RQ3. Further controlled timing runs
are optional if timings are reported descriptively and no causal speedup claim is made.
